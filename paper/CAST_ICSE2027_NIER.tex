\title{CAST: Testing the Attribution Stability of AI-Generated-Code Detectors Under Controlled Source Transformations}

% Double-anonymous submission: author block intentionally omitted.
\author{\IEEEauthorblockN{Anonymous Author(s)}
\IEEEauthorblockA{Submission to ICSE 2027 NIER Track}}

\maketitle

\begin{abstract}
\blfootnote{Code and artifacts: \url{https://anonymous.4open.science/r/cast-icse2027-artifact-4ECD}}
AI-generated-code detectors are evaluated almost exclusively on static snapshots, even though real code is routinely reformatted, renamed, and restructured after creation. We present CAST (Code Attribution Stability Testing), a controlled, distance-instrumented methodology that measures whether a detector's human-versus-AI attribution survives such changes, and uses a canonicalization intervention to diagnose the source of any instability. Evaluating three independently reproducible detectors on 199 held-out Python and Java programs from the Droid corpus, we find that reformatting with a standard tool (\texttt{black}/\texttt{google-java-format}) flips DroidDetect-Base's correct verdict on genuinely human-written code to ``AI'' 58.0\% of the time (29/50 baseline-correct human samples), while leaving its verdict on actually AI-authored code almost unchanged (0.0--4.3\%). A symmetric experiment -- perturbing AI-authored code toward human-like messiness -- induces the reverse, AI-to-human flip at only 5.2\% (5/96), confirming the asymmetry is directional and not a no-op or edit-size artifact, and consistent with the detector having learned tidy formatting as an AI-authorship proxy. LLMSniffer's low error rate is not evidence of robustness: its own accuracy on this corpus (67.0\% Python, 44.4\% Java) is at or below a majority-class baseline. DetectCodeGPT shows broad score movement that a fresh-seed identity control shows cannot yet be distinguished from its own re-scoring noise. Canonicalizing away presentation differences attenuates DroidDetect-Base's residual formatting-induced movement by 14.8--15.4$\times$, though this is complicated by canonicalized input itself becoming out-of-distribution for the detector. Static accuracy alone therefore does not characterize detector reliability under routine code evolution.
\end{abstract}

AI-generated code detection, robustness testing, metamorphic-style evaluation, software evolution

\section{Introduction}

AI coding assistants now write a substantial share of the code developers review, edit, and ship. Detectors that attribute this code to a human or AI origin are typically evaluated the same way a classifier is: on a fixed test set, scored once, with accuracy as the verdict.

\textbf{Motivation:} That protocol quietly assumes the code being judged stays put. It does not. An IDE reformats a file on save, a refactor renames a variable, a reviewer rewrites a loop -- none of it changes what the program does, yet any of it can change what a detector says about who wrote it. A detector whose verdict flips under a cosmetic edit is not measuring origin; it is measuring the snapshot. This is a routine, non-adversarial threat distinct from the adversarial setting the closest prior work targets: robustness studies vary how code is generated~\cite{hidinginplainsight} or train against an attacker's renaming~\cite{codegptsensorplus,droid}, and separate work shows renaming can defeat code watermarks~\cite{codewatermark} and that code-model metamorphic testing treats renaming as standard~\cite{metamorphicslr}. None measures whether an already-trained detector's verdict survives a non-adversarial edit, or reports which edits matter and why.

\textbf{Objective:} This paper's objective is to make attribution stability an explicit, measurable property of an AI-code detector, not an afterthought to accuracy, and to build the smallest instrument that can measure it. We introduce \textbf{CAST} (Code Attribution Stability Testing): given a program of known origin, CAST applies a validated transformation, measures the resulting change at the text, token, and AST level, and records how the detector's score and decision move (Section~II). Where movement is large, CAST adds a second, targeted step: canonicalizing both sides of the pair to test whether the instability is a presentation artifact or something deeper. Applied to three independently reproducible detectors over 199 held-out Python and Java programs~\cite{droid}, this approach exposes stability profiles that a single accuracy number cannot: one detector's instability is almost entirely a formatting artifact that canonicalization removes; another's is not.

This paper makes two contributions.
\begin{itemize}
\item \textbf{CAST}, a controlled, distance-instrumented diagnostic methodology for evaluating the attribution stability of already-trained AI-code detectors under routine, non-adversarial edits, including a canonicalization intervention that isolates presentation-driven instability from a broader failure mode.
\item A held-out evaluation of three reproducible detectors over 199 programs, showing qualitatively different, transformation-specific stability profiles, together with a corpus-composition limitation that bounds this evaluation's current reach.
\end{itemize}

The remainder of the paper is organized as follows. Section~II defines CAST and the canonicalization intervention. Section~III describes the dataset, transformations, detectors, and research questions. Section~IV reports results; Section~V discusses their implications. Section~VI lists threats to validity, Section~VII positions CAST against related work, Section~VIII outlines future plans, and Section~IX concludes.

\section{CAST}

\subsection{Attribution stability}

\emph{Attribution stability} is the degree to which a detector's output for a program is preserved under routine, non-adversarial edits -- distinct from adversarial robustness, which studies a worst-case attacker searching for an evasive rewrite. CAST's transformations are fixed, deterministic operators applied uniformly across the corpus, not an adversarial search against any detector. CAST treats score movement and decision-flip rate as first-class observations, not a single post-transformation accuracy number.

\subsection{Methodology}

For a detector $D$, a transformation $T$, and a program $C_0$ of known provenance, CAST proceeds in five steps.
\begin{enumerate}
\item Apply $T$ to obtain $T(C_0)$.
\item Validate that $T(C_0)$ is well-formed at or above $C_0$'s own syntactic-validity tier. Non-applicable and invalid outcomes are recorded, not discarded.
\item Measure $d_\text{text}$ (character-level edit distance), $d_\text{token}$ (edit distance over the language's own lexical token stream, e.g., Python's \texttt{tokenize} output including \texttt{INDENT}/\texttt{DEDENT}, or Java tree-sitter leaves), and $d_\text{AST}$ (AST node-count change).
\item Score $D(C_0)$ and $D(T(C_0))$.
\item Aggregate, per detector, language, and family, the mean and median score movement $\Delta_D = D(T(C_0)) - D(C_0)$, the decision-flip rate, and the \textbf{Induced Error Rate}, defined as:
\end{enumerate}
\begin{equation}
\resizebox{0.99\columnwidth}{!}{$\displaystyle
\text{IER} = \frac{\#\{\text{baseline-correct programs whose decision flips after } T\}}{\#\{\text{baseline-correct programs}\}}
$}
\end{equation}
IER is conditioned on the detector having been correct on $C_0$. A flip on a program the detector already misclassified would otherwise conflate ordinary detector error with transformation-induced instability. Detectors also expose incompatible score semantics: a calibrated probability, an uncalibrated sigmoid output, or an unnormalized statistic. CAST therefore does not compare raw $|\Delta_D|$ across detectors. IER, a bounded proportion with a consistent interpretation regardless of score scale, is the primary cross-detector metric. Raw score movement is interpreted only within a given detector's own distribution.

\subsection{Canonicalization intervention}

When a transformation family produces large score movement, CAST additionally scores $F(C_0)$ and $F(T(C_0))$ for a deterministic canonicalizer $F$ that removes a specific, named category of variation (in this study: whitespace, blank lines, comments, and quote style, implemented by re-tokenizing the program and rejoining its semantic tokens). A pair for which $F(C_0){=}F(T(C_0))$ collapses to $\Delta{=}0$ by construction. This subset is reported separately from the residual pairs for which a genuine difference remains after canonicalization, so that the diagnostic result is not an artifact of the trivially-resolved cases. A substantial reduction in the residual subset's score movement constitutes intervention evidence that the removed category of variation contributes to the observed instability. It does not constitute proof of a specific internal mechanism.

\section{Study Design}

\textbf{Dataset:} This evaluation uses DroidCollection's~\cite{droid} held-out test split: 199 programs (100 Python, 99 Java), stratified across \texttt{HUMAN\_GENERATED}, \texttt{MACHINE\_GENERATED}, and \texttt{MACHINE\_REFINED}.

\textbf{Transformations:} Three confirmatory families: formatting (\texttt{black}/\texttt{google-java-format}), lexical renaming of one identifier, and control-flow rewriting (one canonical loop-form rewrite), with applicability rate 0.616 and success rate 0.992 among applicable attempts. A fourth stage attempted two deeper families, local structural extraction and semantics-preserving rewriting, reported as a feasibility finding (Section~IV-D), not a confirmatory one.

\textbf{Validation:} Python uses \texttt{compile()}-based validation. Java is tiered, given the corpus's many function/class fragments: \texttt{STANDALONE\_VALID} $>$ \texttt{WRAPPER\_VALID} (compiles inside a synthetic harness, used only as a validation instrument and never scored) $>$ \texttt{STRUCTURAL\_ONLY} $>$ \texttt{PARSE\_INVALID}.

\textbf{Detectors:} Two of five targeted detectors had a released checkpoint runnable as-is; a third (DroidDetect-Base) required reconstructing its architecture from the checkpoint alone. \emph{LLMSniffer}~\cite{llmsniffer} (GraphCodeBERT~\cite{graphcodebert}, supervised-contrastive) reaches 90.0\% on GPTSniffer's Java test subset~\cite{gptsniffer} but only 67.0\%/44.4\% on this corpus (at or below majority-class baseline; Section~VI). \emph{DroidDetect-Base} (ModernBERT-base~\cite{modernbert} with a projection layer and a four-class head) ships a checkpoint with no modeling code; we reconstructed its architecture and validated it against a disjoint dev-split subset ($n{=}24$), reaching 87.5\% accuracy (Wilson 95\% CI [69.0,95.7]). This does not fully contain the 98--99\% test-split accuracy reported in Section~IV-A; we cannot yet rule out that the dev subset is harder, or a genuine reconstruction gap, and flag this as an open validation question (Section~VI) rather than resolving it here. \emph{DetectCodeGPT}~\cite{detectcodegpt} is a zero-shot statistic from the DetectGPT~\cite{detectgpt}/NPR~\cite{detectllm} family, computed from CodeLlama-7B~\cite{codellama} and CodeT5p-770M~\cite{codet5plus}, with $K{=}50$ perturbations per a pre-registered convergence study. Its threshold, calibrated on an independent 40-sample set, reaches only 60.0\% accuracy, so raw score movement is primary evidence and threshold-derived decisions secondary. \emph{GPTSniffer}~\cite{gptsniffer} and \emph{CodeGPTSensor/+}~\cite{codegptsensor} could not be integrated, as neither released a checkpoint; we did not train replacements, to avoid confounds distinct from evaluating a published detector.

\textbf{RQs:} This evaluation is structured around three research questions.
\begin{itemize}
\item \textbf{RQ1:} How stable are detector scores and decisions under formatting, lexical renaming, and control-flow rewriting?
\item \textbf{RQ2:} Do detectors exhibit similar or detector-specific stability profiles under identical transformations?
\item \textbf{RQ3:} Does canonical normalization attenuate transformation-associated instability, and does this differ across detectors?
\end{itemize}

\section{Results}

\subsection{RQ1/RQ2: detector-specific, transformation-specific profiles}

Table~\ref{tab:ier} reports IER with baseline-correct denominators. DroidDetect-Base's formatting IER exceeds its lexical-rename and control-flow IER in both languages, collapsing to at or near 0\% in Python; Wilson~\cite{wilson1927} 95\% CIs for formatting do not overlap the other families in Python, while Java's smaller denominators give wider, overlapping intervals. Table~\ref{tab:byclass} breaks this down by true origin class: DroidDetect-Base's formatting IER is 58.0\% on genuinely human-written code but 0.0--4.3\% on actually AI-authored code, consistently in both languages (Python 66.7\%/0.0\%/6.5\%; Java 41.2\%/0.0\%/0.0\%). This is not a no-op artifact (only 5--6\% of AI-class transforms are byte-identical), and a symmetric check confirms it is directional: messifying AI-class code induces the reverse flip in only 5.2\% of cases (5/96; Section~VI). Raw edit size does not cleanly separate flipped from unflipped human samples once normalized by program length (Section~VI). $|\Delta|$ correlates weakly with $d_\text{text}$ ($\rho{\le}0.30$) but not $d_\text{AST}$ ($\rho{=}{-}0.20$, $0.03$). Of the 29 flipped human samples, four-class output lands mostly on MACHINE\_REFINED (17/29) over MACHINE\_GENERATED (11/29). LLMSniffer's low IER is not robustness evidence (67.0\%/44.4\% baseline accuracy, at/below majority); DetectCodeGPT's elevated IER (16.7--50.0\%) sits within its 30.0\% identity-control noise floor (Section~VI).

A symmetric check -- messifying AI-class code (trailing whitespace, extra blank lines, inconsistent quoting/spacing; validity-checked, semantics-preserving) and rescoring -- induces the reverse AI-to-human flip in only 5/96 baseline-correct cases (5.2\%, 95\% CI [2.2,11.6]; Python 6.5\%, Java 4.0\%), confirming the asymmetry is real and directional, not a no-op artifact.

\textbf{Answer:} DroidDetect-Base's instability is real, class-specific, directionally asymmetric (58.0\% vs.\ 5.2\%), and overwhelmingly false-accusing; the other two detectors' apparent profiles are confounded by degenerate baseline accuracy and re-scoring noise, respectively.

On the residual-only subset -- excluding pairs canonicalization trivially equalizes -- DroidDetect-Base's mean score movement still falls 14.8--15.4$\times$, but this is complicated by an out-of-distribution effect: mean probability on the \emph{true} class drops to 0.223 (66\% $<$0.05) against 98--99\% raw accuracy (Section~VI), so canonicalized input is often confidently misclassified. \textbf{Answer:} Canonicalization sharply reduces DroidDetect-Base's residual movement, though part of this may reflect canonicalized input becoming out-of-distribution rather than purely resolved instability; DetectCodeGPT's movement is unreduced, and on Java, larger after canonicalization.

\subsection{Corpus feasibility for deeper transformations}

Local structural extraction and semantics-preserving rewriting were additionally attempted at two intensities; of 796 attempted combinations, only 37 (4.65\%) were applicable (35 validated, only 4 with true differential-execution verification), reflecting Droid's fragment-heavy composition. The resulting per-detector cells ($n{=}1$--$12$) are illustrative only and support no confirmatory claim.

\section{Discussion}

Static accuracy does not characterize post-transformation reliability, but neither does a low IER by itself characterize stability: LLMSniffer's near-majority-class accuracy makes its low IER a likely degenerate-predictor artifact, and DetectCodeGPT's IER is not yet separated from re-scoring noise. Only DroidDetect-Base's instability survives both checks -- a real detector (98--99\% baseline accuracy) whose formatting sensitivity is reproducible, class-specific, and directionally asymmetric under a symmetric intervention (58.0\% vs.\ 5.2\%; Section~IV-A). This asymmetry, more than the raw and imperfectly length-controlled edit-distance comparison (Section~VI), is what best supports tidy formatting as a learned AI-authorship proxy, though CAST does not identify the mechanism directly. A verdict unfit to survive a random seed or a formatter run is unfit for single-verdict use. Canonicalization remains a diagnostic, not a validated mitigation: its own out-of-distribution effect means a practical fix needs a layout-preserving normalizer instead.

\section{Threats to Validity}

\begin{itemize}
\item \textbf{External:} Two languages, one corpus, three detectors; two others lacked a released checkpoint. Transformation operators represent common tooling edits, not sampled developer histories.
\item \textbf{Construct:} LLMSniffer's baseline accuracy (67.0\%/44.4\%, at/below majority) means its low IER is not robustness evidence. Flipped human samples' smaller raw $d_\text{text}$ tracks their shorter length more than a smaller edit (length-normalized $d_\text{text}/\text{len}$: 0.146 vs.\ 0.136), so program length is an unexcluded confound alongside the class-level effect the symmetric check (Section~IV-A) confirms. Detector scores have incompatible scales; DetectCodeGPT's weak calibration limits threshold-derived results to secondary status, and its IER/$|\Delta|$ are upper bounds including a comparable noise floor. $d_\text{text}$, $d_\text{token}$, $d_\text{AST}$ correlate only weakly with $|\Delta|$.
\item \textbf{Internal:} DroidDetect-Base's architecture was reconstructed absent public modeling code, not yet compared against the original authors' numbers. Its 87.5\% dev-split CI [69.0,95.7] does not fully contain its 98--99\% test-split accuracy -- an unresolved gap (dev difficulty or reconstruction difference) the entire headline finding rests on. IER uses the human-versus-AI collapse of its four-class output (16/365 intra-AI-churn flips excluded). The canonicalizer normalizes several presentation properties at once, so a result is about that combined category; canonicalized-input accuracy shows a real out-of-distribution effect not fully controlled for.
\item \textbf{Corpus:} Droid's fragment-heavy composition limits deeper transformations to 4.65\% applicability and differential-execution verification to 4/35 successful instances; those cells are illustrative, not confirmatory.
\item \textbf{Conclusion:} Some cells have small denominators, as low as $n{=}4$; Wilson 95\% CIs are reported throughout. Cohen's $d_z$~\cite{cohen1988} (in the artifact) is supplementary, directional-consistency evidence only.
\end{itemize}

\section{Related Work}

Measuring prediction change under fixed, semantics-preserving transformations is established for code models generally: Rabin et al.~\cite{rabin} show neural program models fail to generalize under such edits, and ReCode~\cite{recode} benchmarks code-generation robustness under $>$30 similar operators. CAST applies the same style of edit to a different task and failure mode (attribution false-accusation, as a metamorphic relation, not degraded generation), which Table~\ref{tab:novelty} positions against detector papers~\cite{gptsniffer,llmsniffer,detectcodegpt,codegptsensor} (accuracy only, no stratification), CodeGPTSensor+~\cite{codegptsensorplus}/Droid~\cite{droid} (adversarial, not routine), Pordanesh et al.~\cite{hidinginplainsight} (varies generation, not the code), and RoPGen~\cite{ropgen} (trains a \emph{human}-authorship attributor; CAST evaluates \emph{already-trained} detectors). Whitespace-based detection work~\cite{whitespaces} motivates why formatting sensitivity can be presentation-driven.

\section{Future Plans}

This evaluation will be extended in three directions: (1) a layout-preserving normalizer and length-controlled resampling; (2) chained transformations on complete programs mined from commit histories; (3) comparing DroidDetect-Base against the original authors' numbers, shared-seed DetectCodeGPT, and a detector trained against CAST's transformations.

\section{Conclusion}

This paper presented CAST for testing attribution stability. Its clearest finding: a validated detector flips correct verdicts on human code to ``AI'' 58.0\% of the time after reformatting, versus 0.0--4.3\% on AI code and 5.2\% in reverse under a symmetric messiness check -- consistent with tidy formatting as a learned AI-authorship proxy. The other two detectors are confounded by baseline accuracy and re-scoring noise: a low IER alone is not robustness evidence.
